## Module 4: Status workflow (2026-11-22 to 2026-11-24)

- **Tool:** Claude (Sonnet 5.5) in a claude.ai Project chat, using its sandbox to run code.
- **What it did:** Walked through the design decisions with me before any code (the transition table and who may make each move, named workflow functions, where permissions are checked, transactions, concurrency, editing rules, applying extraction results, audit events, error types, resubmission, required fields, whitespace in comments, unexpected extraction errors) and recorded them in `claude/PROJECT_STATE.md` and `claude/WORKFLOW_DESIGN_NOTES.md`. Drafted `app/services/workflow.py` (transition table, named functions, background process function), the `UPLOAD_DIR` setting in `app/config.py`, `tests/test_workflow.py` (203 test cases), the move of the shared test fixtures out of `tests/test_db.py` into `tests/conftest.py` and `tests/helpers.py`, and the README additions (status workflow section, configuration row, Future improvements entries). Ran the tests in its own sandbox against a stand-in migration and mock extractor (243 passed, not counting the 5 smoke tests, which need files it did not have), and deliberately broke the workflow in 16 ways to confirm each break made at least one test fail. It could not run Docker or the real Alembic migration there. After my first run on my machine showed one failing test, it diagnosed the cause (Alembic's logging setup switching off the workflow's logger during the test fixture), reproduced the failure by changing its stand-in `env.py`, and checked two candidate fixes in its sandbox.
- **What I decided or changed by hand:** Chose to keep the first version small: one manager and one employee are assumed, so I declined the AI's suggestion to add manager assignment to the schema and accepted a documented concurrency compromise instead. I questioned the purpose of retry on a receipt with no new input, which led to writing down what retry is actually for. I set the submit rules (positive totals and line item amounts, no future purchase dates, warn only on a totals mismatch) and chose to validate blank comments and missing required fields in the workflow (leaving the database check as a backstop) instead of changing the database. I also decided to trim the ends of every text field and standardize the currency, to reject purchase dates after today's UTC date and accept the time-zone flaw as a documented future improvement, and to clear the failure reason when a retry starts. Placed the new files and applied the edits to `app/config.py`, `tests/test_db.py`, `README.md` and `docs/AI_LOG.md`, and added `UPLOAD_DIR` to `.env.example` by hand. Verified on my machine in the venv: `pytest tests\test_db.py` (20 passed), `pytest tests\test_workflow.py`, the full `pytest`, `alembic check` and a check of the `UPLOAD_DIR` setting. The first run of the workflow tests had one failure, the log assertion in `test_an_unexpected_error_gets_a_generic_reason_and_is_logged`. I made one manual code change to fix it: in `alembic/env.py` I changed `fileConfig(config.config_file_name)` to `fileConfig(config.config_file_name, disable_existing_loggers=False)`, following the AI's diagnosis (the migration run inside the test fixture was switching off the workflow's logger). After that change all the checks ran as expected. Docker was not part of this verification.
